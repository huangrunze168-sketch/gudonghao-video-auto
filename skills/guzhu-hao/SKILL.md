# 股东号：官方联网优先

## 不可违反的决策规则

1. 首先读取项目官方命令清单及相关 help，按工序选择官方能力，不是每个视频机械调用全部命令。
2. 素材默认走官方在线搜索、推荐、下载。缓存只用于复用已验证资源，不能限制审美选项。
3. 缺字体先调用官方依赖下载；不要跳过好看的歌词模板，也不要凭目录存在判断可用。
4. 官方失败先排查工作区路径、命令参数、授权、依赖与实际错误。不得自动使用 Whisper、SAPI、FFmpeg 加工、纯色背景或本地随机素材替代。需要替代必须先获得用户同意。
5. 歌词模板和 TTS 字幕完全独立。歌词保留官方模板的字体、排版、动画；禁止复制 TTS 字幕字体覆盖歌词。
6. 不得将 help、参数报错、目录存在或 SDK 网络规则计数当成业务成功。逐项区分：入口存在、搜索成功、下载实体、依赖齐全、套用成功、导出视觉与声音验收。
7. 不得删除所有 `guzhu-*` 草稿。验证使用独立副本，清理仅限本次拥有的目录。

## 每首歌必须重新设计（禁止套用上一首）

**每次生成新歌，以下四项必须针对这首歌重新设计，不得沿用上一首。**
判断标准很直白：如果两首成片的这四项看起来一样，就是失败，必须重做。

1. **TTS 口播话术**——按这首歌的主题、情绪、场景重新写。不能复用上一首的句式骨架
   （例如上一首用"有没有…／却在…／不是…／只是…"，这一首就不能照搬这个骨架），
   也不能只换几个词。要先读歌词提炼这首歌独有的钩子，再写话术。
2. **贴纸**——按**每句话术的情绪**从官方素材库**在线搜索搞笑表情包**：
   猫、狗、汤姆和杰瑞这类梗图表情包，一句配一个（用户明确要的就是这种）。
   本地贴纸池只是历史上用过的残留，**不能固定用池子里那几个**；也不能换成
   "独处时光""静享慢时光"这类文字贴纸——那不符合用户要的搞笑表情包风格。
   搜索示例：`material search --type sticker --prompt "无奈 搞笑"`、
   `--prompt "开心 狗 表情包"`、`--prompt "猫 无语 表情包"`。
3. **背景图**——按歌曲意境**重新生成或在线选取**。**禁止沿用上一首的背景图**；
   除非用户明确说这幅画面继续用。
4. **歌词模板**——按这首歌的歌词气质**在线搜索**重新挑。不能固定用一个模板
   （上一首用「抒情手写」，这一首就要重新搜、重新选）。

批量场景下，即使同一个模板包，也要逐首替换这四项，而不是共用一套。

## 默认成片要求

- 1280×720，口播加一段副歌约 30 秒；超长结尾渐弱。
- 每首话术可编辑；官方曼波讲故事，1.3 倍速。保留官方原始语音，禁止先本地变速再设段速率；只应用一次剪映官方变速。逐段核对源范围、帧对齐后的目标范围和句间衔接；WAV 编码无损不代表听感合格，必须检查卡顿、截尾和突跳。
- **三条音频通道必须分开设置**，不能合并成一次调音量：
  - 垫乐（片头背景音乐）**-8dB** —— 只负责不盖住人声；
  - **口播 TTS +8dB**（`draft audio volume` 打在 TTS 段上）—— 口播自身要够亮；
    用户指定用 **+8dB**（+3/+6 实测偏闷）。批次字段 `media.intro_volume_db`，不填
    时脚本默认也是 8；
  - 副歌 +3dB。

  **+8dB 会让真峰值越过 0，必须再叠一道真峰值控制**（实测，方案 1）：

  口播 TTS 源文件峰值本就到 **-1.2 dBFS**，再加 +8dB 后成片真峰值会超 0。
  注意**降副歌增益没用**——峰值来自口播段本身。

  正解：**保持 +8dB 不动，只对 `text_to_audio` 段**执行官方归一：

  ```
  draft algo loudness-normalize --seg-id <口播段>
      --target-loudness -11 --true-peak-ceiling -0.2
  ```

  **背景垫乐（`extract_music`）与副歌段绝对不要动**，否则会破坏三条通道的关系。
  脚本：`scripts/guzhu_peak_ceiling.py [项目目录名]`（传项目名可避免误伤别的项目）。

  **本机 11.5.0.14471 的两条实测限制，必须知道**：

  1. **`--true-peak-ceiling` 未真正生效**：设 -0.2 或 -0.5，成片左声道峰值仍是
     **+0.01 ~ +0.02 dB**（用 `ffmpeg -af astats=metadata=1:reset=0` 量，比
     `ebur128` 精确）。这个量级是 **AAC 编码过冲**，听感无影响，但严格说 >0dBTP。
  2. **`loudness-normalize` 对同一段是幂等的**：改 `--target-loudness`（-11 → -12）
     重复调用不会改变结果，响度与峰值都不动。要真正降峰值，只能**降低口播段增益**
     （`media.intro_volume_db` 从 8 调到 7.5 左右）。

  结论：**+8dB 与"严格 ≤0dBTP"在本机不能同时满足**。要么接受 +0.02dB 的编码过冲
  （听感无差），要么把口播设为 7.5dB。**每次都要用 astats 复测，不要只看 ebur128 的
  0.0/0.1 读数。**

  口播与背景是**两条独立通道**：调背景不会改变口播。过去只调了背景，口播一直停在
  原始音量，听着就没劲，这是最常见的一处漏项。响度归一（`algo loudness-normalize`）
  不能替代这三条，逐段归一反而会破坏相对音量，启用必须独立混音验证。
  核对源文件是否已烘焙增益，禁止再次叠加模板段音量。原始素材由官方段增益设置目标值；历史已加工素材须取消重复增益，不能把段音量直接当作最终有效增益。
  测量最终导出文件的立体声真峰值；超过 0dBTP 必须修复后重导出，不能宣称音质已验收。
- 用户 TXT/LRC 为歌词文本依据，官方识别为时间依据。修改后必须逐句检查文本与音频，不允许重复字、均分时间伪装同步。
- **选段必须按用户歌词里的段落标记**。歌词文件常写 `[Chorus 1 - Open, Emotional]` 这类标记，
  **标记就是副歌起点的权威依据**，不要用响度/能量检测去猜（实测会选错段）。
  解析要求：
  - 方括号段落标记可能很长（实测 27 字符），**不能限制长度**，否则整行会被当成歌词、副歌定位失效；
  - **所有** `[Verse]/[Pre-Chorus]/[Bridge]/[Final Chorus]` 标记都要剔除，不能留在歌词里；
  - **`pre-chorus` / `post-chorus` 不是副歌起点**，它们也含 "chorus"，必须先排除，
    否则副歌会提前整整一段（实测早 4 行）。
  - 解析后核对：副歌起始行对应的歌词，必须真的等于 `[Chorus]` 之后的第一句。
- **片头每一句口播都要配贴纸**。贴纸、口播字幕、TTS 音频是三个独立对象，模板本来就是
  "每组一个贴纸"；不要因为字幕已经存在就省略贴纸，也不要把贴纸只挂在第一句上。
  贴纸按该句话术情绪在线选取，小尺寸，位于字幕正上方、不遮挡。

  **TTS 口播字幕的字号/缩放必须逐首按最长句重算**（实测踩坑，每次都漏）：

  模板给 subtitle 段预设了 `clip.scale`（实测 `2.1546`）与字号 `5`，那是按模板原本的
  短句调好的。换成长句就会被**左右切掉**——实测 22 字的
  「我们不是不合适 是太合适了 合适到谁也走不了」两边都吃字，
  而 19 字的句子在默认缩放下只是勉强贴边。

  **每首歌话术长度不同，所以每次都要重新算，不能沿用上一首的缩放值。**

  实测校准基准：**19 字在 `scale=1.6747` 时恰好占满宽度且不裁字**。
  于是按最长句反算，并留约 6% 余量：

  ```
  scale = 1.6747 × 19 / 最长句字数
  ```

  实测：22 字 → `1.36`，渲染抽帧确认完整显示、左右有余量。
  脚本：`scripts/guzhu_tts_fit.py`（读草稿里的 subtitle 段，按最长句改 `clip.scale`，
  自动对齐 timeline.id 后重导出）。**设置后必须渲染抽帧确认，不能只看数值。**

  **贴纸大小的正确通道**（实测踩坑）：官方贴纸命令只有 `add` / `remove` / `translate`，
  **没有缩放命令**；改段上的 `clip.scale` **对渲染完全无效**；`draft video scale` 也会拒绝
  sticker 段。真正生效的是**段级 `common_keyframes`** 里的 `KFTypeScaleX` / `KFTypeScaleY`
  —— 改这些关键帧点的 `values` 才会改变渲染尺寸。
  取值参考：模板常见值 `0.22` 偏小，**0.5–1.0 比较合适**；`2.0` 会占满画面并遮挡歌词。

  **新贴纸段默认没有缩放关键帧，必须自己按官方结构创建**（否则用素材原始尺寸，
  实测「想你」那张白猫会铺满整个画面）：

  ```json
  {"id": "<uuid>", "material_id": "", "property_type": "KFTypeScaleX",
   "keyframe_list": [{"id": "<uuid>", "left_control": {"x":0,"y":0},
                      "right_control": {"x":0,"y":0}, "values": [0.5]}]}
  ```

  X/Y 两组都要建（值相同）。实测 0.5 时贴纸约占画面 1/3 高度、位于字幕上方不遮挡。

  **另一个坑：`media.stickers: "auto"` 会用模板预置的那几个贴纸**，实测两首歌跑出来
  竟然是同一批（二哈、猫和老鼠、汤姆猫），直接违反"每首四项必须重新设计"。
  **必须在流程后显式删除旧贴纸、再按本首歌的情绪逐个加入在线搜到的表情包。**
  片头每一句口播都要配贴纸。
- **歌词套剪映官方的歌词模板，并从几十个里挑一个适合这首歌的**（批次 `lyrics.animation` 填模板 id）。
  保留官方模板的字体与排版，**不要用本地字体库存筛掉在线候选，也不要自行替换字体**。
  让官方模板套用流程处理依赖；遇到真实错误记录并排查，不承诺一定回退或必然可用。
  挑选时核对两件事：
  - **意境贴合**：独处/夜晚/抒情 → 雨雾氛围感、抒情手写、淡蓝抒情；古风 → 国风大字、书法大字；
    摇滚 → 节奏摇滚；复古 → 文艺复古、KTV复古字幕；温柔 → 温柔小情歌、粉笺心语。
  - **居中显眼且不溢出**：以实际抽帧为准，不以模板字号数字或名称推断位置、大小。不同模板的字号基准不同；检查完整句子和动画过程，拒绝裁字、重复字与边缘小字。

  挑模板的正确路径：
  - 搜索：`material search --type lyric_animation --prompt "<意境短词>"`（如"抒情 歌词""复古老歌词"）。
    **用意境短词，不要丢整句歌词**——后者返回的多是"有点甜""音乐播放器"这类无关模板。
  - **全量枚举**（比搜索更全）：`material topic --type lyric_animation --id 11878 --limit 50`，
    分页用 `--cursor`，取值来自返回的 `next_offset`。官方共 **105 个**歌词模板。
  - **不要只在本地 `Cache/artistEffect` 里翻**：那只是"历史上被用过"的残留，
    不代表可选范围（几十个模板在线上）。

  **本地备用库（已全量下载 + 全量实测）**：`work/guzhu-templates/library/index.json`（102 个成功），
  模板重建质量排名见 `work/guzhu-templates/template-ranking.json`，

  ### 字体：模板外观的关键，必须单独核对（实测踩坑）

  **只套模板不等于套上了模板的外观**。实测 102 个模板：

  - 共依赖 **115 个字体，其中 47 个不可用**——目录里只剩 `font.lock`，**没有 `font.ttf`**，
    属于"假下载"；渲染时字体回退，成片会变成默认发光体，**与剪映里看到的效果完全不同**。
  - 修复前：字体齐全的模板仅 **46 个**；补齐后 **75 个**。

  **官方 CLI 的字体下载有 bug**（实测）：

  ```
  upstream -100202 / resource_pool -7002 / download -1008 / cannot unzip file
  ```

  即服务端返回的字体包在 CLI 侧解压失败（包内中文文件名编码问题）。
  **剪映 GUI 用另一套解压逻辑所以能正常下载**，这正是"你在剪映里没问题、脚本却不对"的原因。

  **绕过方式（仍走官方接口，不是本地替代）**：

  1. `material query --type font --resource-id <id>` 拿到官方签名 CDN 地址与 md5；
  2. Python 直接下载并用 `zipfile` 解压（不依赖 CLI 的解压路径），**校验 md5**；
  3. 把字体文件放到 `Cache/lyra-cli/material-cache/font/<font_id>/font.<ext>`。

  设置字体用 `draft text style --font <font_id>`，注意 **`--seg-id` 只能逐个段传**，
  逗号分隔会报 `expects raw segment ids`。

  **关键：字体必须落到三处，缺一处就回退默认字体**（实测确认的根因）。

  官方正常下载一个字体时是这样写的：

  ```
  Cache/lyra-cli/material-cache/font/<font_id>/font.ttf       # 资源本体
  Cache/lyra-cli/material-cache/font/<font_id>/font.lock      # 草稿 font.path 指向它，渲染器直接读这个文件
  Cache/lyra-cli/material-cache/font/<font_id>/<font_id>/<原名>.ttf + config.json
  Cache/effect/<font_id>/<原名>.ttf
  ```

  **最要命的是 `font.lock`**：草稿里的 `content.styles[*].font.path` 就是
  `.../font/<font_id>/font.lock`，渲染器按这个路径读字体文件。
  官方字体下载失败时它是个 **0 字节的锁文件**，于是渲染**静默回退默认字体**；
  把它删掉则会直接报 `草稿引用的本地资源不存在: .../font.lock`。

  **所以修字体必须把真实字体内容写进 `font.lock`**，只放 `font.ttf` 是不够的
  （实测：只放 font.ttf 时画面始终是默认黑体；写入 font.lock 后立刻变成模板的手写体）。
  `config.json` 内容为紧凑格式
  `{"effect":{"Link":[{"type":"InfoSticker"}]},"version":"3.1.1"}`。

  排查时先读草稿的 `content.styles[*].font.path`，确认它指向哪个文件、那个文件是否 >1KB。

  **以上两点已固化为可复用脚本** `scripts/guzhu_fonts.py`：

  ```powershell
  python scripts/guzhu_fonts.py audit                  # 审计所有模板的字体依赖
  python scripts/guzhu_fonts.py ensure --all           # 补齐所有缺失字体（含 effect 目录）
  python scripts/guzhu_fonts.py ensure --template <id> # 只补某个模板需要的字体
  python scripts/guzhu_fonts.py fetch --font-id <id>   # 补一个字体
  ```

  状态含义：`ok` 两处齐全；**`half(font-only)` / `half(effect-only)` 是没修干净**
  （只写了一处，渲染仍会回退）；`lock-only` 是假下载；`missing-dir` 完全缺失。
  **每次换模板后都该先跑一次 `audit`，确认目标模板不是 `partial`。**

  **判定字体是否生效必须看抽帧画面，不要只比对 font_id**（实测教训）：
  全量渲染 102 个模板时，若只取 `text_style.font_id` 字段，46 个模板会被误判为"未声明字体"；
  **递归扫描 LyricStyle.json 里所有字体类字段**后才能得到完整声明集合。
  用完整集合复核的结果是：**99 个成功渲染的模板全部匹配（0 不匹配、0 未声明）**，
  即字体没有再回退默认。检测脚本见 `work/guzhu-test/audit_font_match_full.py`，
  结论见 `work/guzhu-templates/font-match-audit.json` 与
  `work/guzhu-templates/108模板渲染验收.md`（99/102 成功）。

  **"与剪映官方效果一致"的可验证依据**：套模板走的是官方 CLI，与 GUI **同一个模板引擎**，
  因此一致性取决于两点，都可逐项核对：
  1. **字体文件齐全**（`font.lock` 有真实内容，不回退默认）—— 已全量核对；
  2. **模板定义的样式确实写进了草稿**（字体、字号、颜色、阴影等）—— 实测抽样一致：
     雨雾氛围感草稿里为 `font=7340606325656654345`、`size=16`、白色 + 橙色配色 + 黑阴影，
     与模板定义的 `font_id`/`font_size:16`/`text_color:#FFFFFF` 吻合。

  **另一个坑**：渲染副本草稿必须对齐 JYPACK 的 `timeline.id`，否则原生渲染直接报
  `没有找到同一 timeline id 的已导入草稿`。

  ### `animation add` 报 "multiple lyrics recognize tasks" 的根因与解法（重要）

  **不是 CLI 的限制，是草稿里累积了多组任务记录**：

  ```
  config.lyrics_taskinfo     反复识别/套模板会累积（实测累积到 11 组）
  config.subtitle_taskinfo   同样累积（实测 3 组，其中两组的 id 完全相同）
  ```

  只有当这两者都只剩 **1 组**时，`draft lyrics animation add`（作用于整组已识别歌词，
  最接近 GUI 的"应用到全部歌词"）才可用；否则报
  `patch apply failed: multiple lyrics recognize tasks found`。

  **清理规则**：只保留 `materials.texts[*].recognize_task_id` 实际引用的那一组，
  并按任务 `id` 去重。清理脚本：`work/guzhu-test/clean_task_groups.py`。

  实测清理后 `animation add` 立即成功；且 **`add` 与 `update` 两条通道的渲染结果视觉一致**
  （同一手写体、同一位置、同一发光效果），说明本 skill 用 `update` 的流程没有引入偏差。
  因此**换模板前后都该检查任务组数量**，避免草稿越用越脏。

  ### 模板重建质量分级（102 个逐个套用实测）

  对全部模板在干净草稿上套用后比对重建文本，**相似度上限 0.849**，且**所有模板重建出的文本完全相同**。
  这证明一个关键事实：**重建文本来自官方 ASR，与模板无关**——错字（如"审判"识别成"在身旁"）
  是识别源头造成的，**换模板解决不了**。

  - **A 级（34 个）**：无同起点重叠、无重复字、达相似度上限。**段数越少越干净**（段少=整句对齐）：
    雨雾氛围感(6段)、星闪发光(7)、弧形播放器(10)、KTV复古字幕(12)、梦幻回忆(12)、发光手写(12)、
    文字拆分(13)、蓝色发光(13)、清叙(17)、emoji律动(18)、文艺复古(19)、红白书法(23)…
  - **B 级（24 个）**：无重叠无重复，相似度略低。
  - **C 级（19 个，必须避开）**：**有同起点重叠**，会让同一时刻多段文字同时显示：
    书法大字(27处)、粉红三行滚动(14)、浪漫氛围(14)、**白色镂空(12)**、随写留痕(12)、
    蓝白律动(7)、黑胶唱片机(6)、多彩粗体(6)、国风大字(4)、节奏摇滚(4)、**长句Emoji(3)**…
  - **失败（25 个）**：依赖缺失、无法套用（轻松律动、文艺抒情歌、樱花飘落、岛屿叙事、花好月圆…）。

  **选模板的规则**：
  1. **先看"重叠数"**，必须为 0——有重叠的模板会把同一句渲染多次，观感直接崩坏，
     这比字号大小重要得多；
  2. 再在 A 级里**优先选段数少的**（雨雾氛围感 6 段），段结构与整句歌词天然对应，最好对齐；
  3. 字号只决定观感大小，可用贴纸缩放那套思路另行调整，不作为首要筛选条件。
  - 套用失败时读取完整官方错误，按实际返回核对资源位置和明确依赖；不要把单次路径问题概括为固定缓存规则。
    禁止全量复制缓存、遍历任意数字猜依赖类型，或用目录存在宣称可套用。先使用官方查询、下载及套用命令排查。
  - 套模板后再次逐句核对歌词，保留官方双行或分段排版；修正文案不能把换行拍平成长行，必须抽帧检查全句没有裁字。
    **注意**：按上面的正确顺序（先套模板、后写文本）操作时，文本不会再被重建覆盖，
    通常不需要逐段校正；只有在"先写后套"的旧顺序下才需要事后补救。

  若确实想完全避开模板依赖，可写 `lyrics.animation: "none"` 用官方识别的默认字幕样式，
  但**默认做法是挑一个贴合意境的模板**，而不是一律不套。

  **歌词文本必须在套模板之后写入**（关键顺序，实测确认的根因）：

  官方套用歌词模板时会**重新识别并重建歌词文本段**（实测同一草稿套一次模板后，
  歌词段数直接从 6 变成 12）。因此如果像历史实现那样"**先写用户歌词、再套模板**"，
  刚写进去的文本立刻被重建覆盖，于是出现重复字与漏字
  （"我我不再""在在""你爱过都"缺"没爱"），每次套完都得事后逐段校正——
  **这不是官方 CLI 的缺陷，是调用顺序错了**。

  正确顺序：
  1. `draft lyrics recognize`（识别）；
  2. `draft lyrics animation update --resource vimo://<id>`（**先套模板**）；
  3. **最后**才把用户歌词写入（`overwrite_lyric_text`）——此时不会再被覆盖。

  另注：`draft lyrics animation add`（作用于"当前歌词结果"，带 `--cover-old`，
  用于替换已有动效）与 `animation update`（作用于指定段）是两条不同通道；
  `add` 只在草稿里**只有一组歌词**时可用，多组会报
  `multiple lyrics recognize tasks found; use update with --target`。
- **画面特效与歌词模板是两回事，必须分别处理**：

  ### 画面不能单调：每首都要叠氛围层（用户明确要求）

  **只做"背景图 + 歌词 + 贴纸"会让画面很单调**（实测成片几乎静止、无层次）。
  必须再叠三层，缺一层就显得单薄：

  1. **运镜/动态** —— 静态背景图必须加缩放或平移关键帧（`draft keyframe add`），
     让画面缓慢推近或平移，绝不能一张静图定到底；
  2. **多个低强度特效** —— 段特效同一时刻只留一个，**要叠加必须走全局效果轨**
     （`draft effect add --resource vimo://<id> --start <t> --duration <d>`）。
     按意境选 **2–3 个**：海岛/温柔 → 光斑流动、细雨、梦幻漏光；
     激烈/都市 → 故障噪点、胶片闪切、暗角划痕。强度统一 **0.10**；
  3. **全局调色** —— `draft adjust add --saturation 8 --color-temperature 6 --shadow 5
     --contrast 4`（提饱和、暖调、抬阴影），让生成的背景图不那么"平"。

  实测：加之前成片 6.8 MB、画面接近静止；加上梦幻漏光 + 光斑流动 + 细雨 + 暖调后
  出现明显星光与暖调层次，文件 8.4 MB。**每首都要按意境重新选，不能沿用上一首那套。**
  输出目录：`work/guzhu-test/add_atmosphere_quNideDao.py` 可作为参考实现。

  **已知未解**：歌词模板（如「发光手写」12 段）遇到长句也会横向超出画面被切
  （实测「岛外一望无际」右边的"际"被裁）。

  **歌词段绝不要用 `clip.scale` 去缩**（实测有副作用）：
  模板的竖排/多色歌词**位置由 `clip.transform` 决定**，整体缩放会把边上的字推出画面
  （实测「文艺复古」整段缩放 ×0.771 后，左侧竖排的"句该听见"被切掉一半）。
  **若某模板确实超宽，正确做法是换模板，而不是缩放。**

  **选歌词模板必须检查"在背景上的可读性"**（除了重叠数、字体齐全之外）：
  - **位置**：是否居中。实测「清叙」歌词偏下偏左，压在暖色背景上几乎看不清；
  - **颜色对比**：发光的浅色歌词在明亮背景（如雨夜暖光街景）上会糊在一起；
  - **是否竖排**：竖排模板（如「文艺复古」）更容易被画面边缘裁字；
  - **稳定性**：实测「星闪发光」在本机套用时崩溃
    （`internal error: process terminated by unhandled Windows exception 0xC0000005`），
    遇到这种就换模板。

  **重跑 build 会重置所有后处理**（贴纸替换、贴纸缩放、字幕自适应、峰值控制、氛围层
  全部要重做一遍），所以**换模板要一次定好再跑**，不要反复重跑。
  统一后处理链参考实现：`work/guzhu-test/finish_zaijian.py`。

  以下为画面特效与歌词模板的区别：
  - **画面特效**（`draft video effect add`）打在**主歌画面段**上，例如胶片噪点、港风胶片、富士影片——它改变的是画面质感；
  - **歌词模板**（`draft lyrics animation update`，`--resource vimo://<lyric_animation>`）打在**歌词文字段**上，决定字体、排版与出字动画。

  两者互不替代：套了歌词模板**不等于**加了画面特效，反之亦然。只做其中一项就是漏项。
  验证画面特效时同时检查独立效果轨和视频段的 `extra_material_refs`；无独立效果段不能判定没加。
  素材存在或官方返回成功也不足以判定生效：核对引用目标、覆盖时间与启用状态，并用有/无效果的同帧对比验证渲染。
  按意境选择实际需要的官方能力（运镜关键帧、转场、调色、画面效果、音频增益与渐弱等），不为凑数量堆叠功能。

  **画面特效要按歌词意境多叠几个，强度调低**（用户明确要求）：
  - **段特效同一时刻只保留一个**：连续 `draft video effect add` 到同一个视频段，
    最终只会剩最后一个（实测加了 3 个只剩 1 个）。要叠加必须走**全局效果轨**
    `draft effect add --resource vimo://<id> --start <t> --duration <d>`，
    它会在草稿里生成独立的 `effect` 轨道。
  - 推荐组合：段特效挂主特效（有 `effects_adjust_intensity` 的，如梦幻漏光），
    其余氛围特效（细雨、婆娑光斑）走全局效果轨。
  - **强度**用 `draft video effect update --seg-id <主视频段> --resource-id <rid>
    --params-json '{"effects_adjust_intensity":0.1}'`；强度 10 即 **0.10**。
  - **注意**：不是每个特效都有强度参数。实测「细雨」「婆娑光斑」**只有
    `effects_adjust_speed`**，没有 `effects_adjust_intensity`；这类特效设强度不会生效，
    要如实说明，不要宣称已调低。
- 背景、画面特效、歌词模板都按歌曲意境选取，不固定沿用同一套。用户要求生成背景时使用相应图像技能，不擅自生成替代画面。

### 新歌素材准备（两个实测坑，已脚本化）

1. **只读属性**：从只读附件复制来的 wav 会带 `ReadOnly`，脚本读取时报
   `[WinError 5] 拒绝访问`。**必须先清除只读属性。**
2. **源文件被覆盖**：把源 wav 放在 `<out>/songs/` 下时，脚本裁剪前会先
   `unlink()` 同名目标（正好是源），随后 ffmpeg 报"没有找到文件"，**源文件也被删掉**。
   **素材统一放 `<项目>/input/`**，与脚本输出目录分开。
   `guzhu_batch.py` 现在检测到同名冲突会自动改用备用名，但不要把素材放进 songs/。

```powershell
python scripts/guzhu_prepare.py <项目名> <wav路径> <歌词txt路径> [歌曲显示名]
```

### 一批到底的流程（避免反复重跑）

**重跑 build 会重置全部后处理**（贴纸替换/缩放、字幕自适应、峰值控制、氛围层都要重做），
所以**模板要一次定好**，不要反复重跑。推荐顺序：

```
1. python scripts/guzhu_prepare.py ...        # 准备素材（去只读、独立 input）
2. python scripts/guzhu_fonts.py ensure --template <模板id>   # 补字体
3. python scripts/guzhu_batch.py run --batch <batch.json>     # build + export
4. python scripts/guzhu_finish.py <项目名>     # 贴纸/字幕/峰值/氛围 一次做完再导出
```

`guzhu_finish.py` 做的事：替换模板预置贴纸为在线搜的 → 贴纸缩放到 0.5 →
口播字幕按最长句自适应 → 口播段真峰值控制 → 段特效 + 全局特效 + 全局调色 → 导出。
**它不会改歌词段的 clip.scale**（会让竖排歌词被推出画面）。

## 官方运行约定

`lyra-cli` 是剪映自带入口，通过项目 `engine/draftediting_runtime.py` 的授权宿主调用。必须保持剪映运行并登录。

**素材命令使用独立 ASCII 可写工作区**（例如系统临时目录），不是中文项目目录 `engine`。在该目录下保存下载及输出，并仅授予实际所需读写路径；不放开整个 Documents 或用户目录。

本项目已接入 `DSH_LYRA_ALLOW_NETWORK=1`。此为项目桥接开关，不是官方 CLI 参数。不得向不支持的命令添加 `--network-mode`。

可复用在线调用器：

```powershell
python scripts/official_materials.py --project "<项目路径>" --type sticker --prompt "悲伤" --limit 5
python scripts/official_materials.py --project "<项目路径>" --type sticker --resource-id "<官方搜索结果ID>"
```

## 工作流与验收门禁

1. **检查**安装版本、账号、输入歌曲/歌词/模板及目标规格。官方帮助无 `err_code` 的纯文本不能算业务失败，应通过专用 help 探测读取；不要改业务成功判定。
2. **在线选材**：按意境搜索歌词模板、贴纸、滤镜/特效/转场，记录搜索词、名称、类型、ID、权益信息。类型以当前官方 help 为准，不能混用 `subtitle_template` 与 `lyric_animation`。
3. **下载及依赖**：下载主资源，按官方模板明确依赖清单下载字体/动画。只剩 lock 不算成功；检查非空字体文件与真实字体路径。不要把任意长数字都当依赖。
4. **隔离套用**：在独立草稿副本识别歌词，再套官方歌词动画。确认实际写入与资源路径；发生字体解压错误必须保留完整 upstream 错误，不宣称解禁。
5. **制作**：官方 TTS、**口播增益**、**每组贴纸**、歌词识别与歌词模板、**画面特效**、转场、段编辑。
   片头与主歌的工序清单**缺一不可**，交付前逐项核对：
   - 每个片头组都有贴纸吗？
   - 口播段上有没有独立的 +8dB（而不是只调了背景）？
   - 主歌画面段上有没有画面特效（而不是只套了歌词模板）？

   同时保持歌词模板与 TTS 字幕两条通路，文本覆盖要验证模板重建后仍正确。
6. **自检导出**：官方 lint 诊断保存到持久输出目录，保留完整 issues/verdicts。退出码不等于所有错误都是渲染失败，空间叠加也不能未经检查全部忽略。镜像四份时间线同步后原生导出。
7. **真实验收**：抽帧及听音，核对字体、歌词同步、贴纸遮挡、口播速度、增益与渐弱、规格时长。官方返回成功不代表成片可交付。
